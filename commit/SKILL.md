# Commit

実装後の変更をそのままコミットせず、先にセルフレビューし、論理的な単位へ分割する。

## When To Use

- 実装が一通り終わったとき
- 変更が複数ファイルや複数関心事に跨るとき
- コミット粒度とメッセージを整えたいとき

## Review Axes

- 命名
- 一貫性
- ビジネスロジック
- 安全性
- パフォーマンス
- コンテキスト適合

## Workflow

1. 変更内容を目的と照合する
2. 6観点（命名、一貫性、ビジネスロジック、安全性、パフォーマンス、コンテキスト適合）でセルフレビューする
3. スコープ外変更を「除外確定」「別コミット候補」に分けて整理する
4. 論理単位でコミット分割案を作る
5. 各コミットに英語の Conventional Commit を付ける
6. 検証状況と `git add` 対象の方針を添えてコミット準備を整える

## Guardrails

- 計画外の変更をコミットに混ぜない
- 無関係な整形やリファクタリングを混ぜない
- 別コミット候補は「価値はあるが今回の目的から分離すべき変更」として扱う
- テスト未実施なら未実施と書く
- 検証状況には自動テスト、手動確認、未確認の別を明記する
- 手動確認は「実施」「未実施」「不明」のいずれかで書く
- 分割はファイル単位ではなく責務単位で考える

## Output Format

- 変更要約
- セルフレビュー結果
- スコープ外変更
- 除外確定
- 別コミット候補
- コミット分割案
- コミットメッセージ案
- 検証状況
- `git add` 対象方針
- 残課題
