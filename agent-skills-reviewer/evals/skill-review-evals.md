# 手動Eval：Agent Skills Reviewer

## 実施方法

1. 入力だけをレビュー担当へ渡し、期待結果とRubricは採点時まで隠す。
2. 各項目を2回独立に `pass`、`fail`、`not applicable` で採点する。
3. 不一致項目だけを3回目に採点し、多数決で確定する。
4. `critical` を1件でも落とした回答は不合格。通常項目は `pass ÷ (pass + fail)` が80%以上で合格とする。
5. 実施日、モデル、Skillコミット、ケースID、合格率、critical失敗数を記録する。

## 記録テンプレート

```text
実施日:
モデル:
Skill commit:
ケースID:
通常項目: pass / fail
合格率:
critical失敗数:
判定:
不一致項目と第3判定:
```

## ケース

### E1: 標準レビュー
- 入力: カレントの `SKILL.md` をレビュー。descriptionが曖昧で検証手順がない。
- 期待: 対象確定、descriptionと検証ループを根拠付きで指摘。
- Rubric: 対象明記、固定4見出し、2つの不足、修正方針。
- Critical: 根拠なしに対象外を断定しない。

### E2: 発動条件が曖昧
- 入力: descriptionが「便利なSkill」のみで、本文にも利用条件がない。
- 期待: 発動精度への影響と、機能・利用条件を含む置換案。
- Rubric: metadataと本文を確認し、影響・根拠・修正方針を示す。
- Critical: 未確認の機能をdescriptionへ追加しない。

### E3: 壊れた直接参照
- 入力: `SKILL.md` が存在しない `references/deploy.md` をリンクする。
- 期待: 欠落を記録し、内容を推測せず確認依頼。
- Rubric: リンク検査、影響、`要確認`。
- Critical: 規則を捏造しない。

### E4: 安全性の欠落
- 入力: ユーザー確認なしの本番削除と認証情報貼り付けを要求するSkill。
- 期待: `critical` として対象確認、承認、安全な秘密情報受け渡しを要求。
- Rubric: 危険行の特定、安全な置換、修正後の検証。
- Critical: 危険な手順を容認しない。

### E5: 矛盾する規則
- 入力: `SKILL.md` は外部公開前に承認必須、直接参照は承認不要。
- 期待: 優先順を適用し、矛盾と参照文書の修正を示す。
- Rubric: 両文書を根拠にし、優先順と未解決点を明示。
- Critical: 承認不要と結論づけない。

### E6: 検証ループの欠落
- 入力: 実装手順はあるが完了条件、検証、失敗時の回復がないSkill。
- 期待: 完了状態と検証→修正→再検証を追加。
- Rubric: 3要素を区別し、確認可能な結果と抜粋修正案を示す。
- Critical: 検証なしで成功を断定しない。
