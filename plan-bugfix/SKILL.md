# Plan Bugfix

不具合修正の前に、仕様かバグかを切り分け、根本原因ベースで修正計画を作る。
その場しのぎの修正案は避ける。

## When To Use

- 障害報告や不具合報告を受けたとき
- 期待動作が仕様かバグか曖昧なとき
- 実装修正の前に再現条件と原因を整理したいとき

## Workflow

1. 事象を一文で整理する
2. 期待動作と実際動作を分ける
3. 観測事実と未確認事項を分け、仕様未確定なら確認事項を先に出す
4. 仕様かバグかを暫定判定し、根拠と不足情報を添える
5. 再現条件と観測点を整理する
6. 根本原因候補、調査対象、修正案、テスト計画を作る
7. 承認前プレビューとして、次に人間が判断すべき点と推奨アクションを一段で要約する
8. 人間の承認待ちで止まる

## Guardrails

- いきなり修正コードを書かない
- 観測事実と推測を分ける
- 応急処置だけの案は避け、根本原因を優先する
- 仕様未確定なら先に確認事項を出す
  - これは本文先頭に別節を足す意味ではなく、`仕様かバグか` で不足情報を明示し、`要確認事項` に確認先と確認内容を優先度付きで出す意味とする
- 仕様かバグかは断定せず、暫定判定の根拠と不足情報をセットで書く
- 承認前プレビューでは「この場では実装しない」ことを明示する
- 未整理の情報を補う仮説は置いてよいが、未確認と明示し、原因候補・観測点の粒度を超えて実装詳細に踏み込まない
- 設計書がない前提で、現行コードと再現結果を根拠にする

## Output Format

- 成果物は下記の各見出しをこの順で埋める。冒頭に別の要約節は足さない
- 事象の整理
- 期待動作
- 実際動作
- 仕様かバグか
- 再現条件
- 根本原因候補
- 調査対象
- 修正案
- テスト計画
- 要確認事項
- 承認前プレビュー
  - 1段落または3項目以内で書く
  - 推奨アクション、保留条件、この場では実装しない旨を含める
- 承認待ち
