# PR Feedback

PRコメントを1件ずつ場当たりで直さず、分類と計画を先に行う。
必要なら同種問題の横展開も確認する。

## When To Use

- PRにレビューコメントが付いたとき
- 指摘を分類して効率的に処理したいとき
- 修正方針と返信文案をまとめて作りたいとき

## Comment Types

- コード修正
  - 現PRで直すべき不具合、安全性、仕様逸脱の修正
- 設計変更
  - 責務分離、レイヤ追加、データ構造見直しなど構造変更。合意前は調査と提案まで
- 質問
  - まず回答や確認で返す。修正依頼が明示されるか、合意が取れるまで実装しない
- 軽微指摘
  - typo、文言、限定的な命名調整など、影響範囲が狭い小修正

## Workflow

1. 未解決コメントを列挙する
   - 1コメント1項目で扱う。スレッド全体は1件にまとめない
2. コメント種別ごとに分類する
3. 各コメントの意図を要約する
4. 必要な調査と修正方針を決める
5. 関連箇所への横展開が必要か確認する
6. 実施前プレビューを作る
   - 「このPRでやること」「このPRではやらないこと」「先に確認すること」を明示する
   - 実施前プレビューはコメント単位ではなく、PR全体の実施範囲サマリとして書く
7. 修正後の返信文案を作る

## Guardrails

- 指摘箇所だけを機械的に直さない
- 質問コメントは、明示的な修正依頼か合意が出るまで回答と確認を優先する
- 設計変更は承認前に大きく進めない
- 承認とは、このPRで進めることについてレビュアーとPRオーナーの認識が揃った状態を指す
- 返信では何を直したか、何を確認したかを明確に書く
- 設計書がない前提で、コメントと既存コードを根拠にする

## Output Format

- コメント一覧
  - 各コメントは「対象」「分類」「意図要約」を最低限含める
  - 原文を丸ごと再掲せず、判断に必要な粒度で1コメント1項目に要約する
- 分類結果
  - コメント一覧の繰り返しではなく、種別ごとの件数または代表項目の要約を書く
- 対応方針
- 横展開確認
  - コード未確認なら、実査結果ではなく「確認観点」と「確認対象の当たり」を書く
  - コード確認後に初めて、該当有無と同PRで直す範囲を確定する
- 実施前プレビュー
- 修正計画
  - 対応方針が「何をどう扱うか」なら、修正計画は「どの順序で進めるか」を書く
- 返信文案
  - 原則としてコメントごとに分けて書く。PR全体コメントは要約が必要なときだけ追加する
- 要確認事項
